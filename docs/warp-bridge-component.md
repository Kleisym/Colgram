# Мост: как он устроен и почему он один

Файл: `tools/warpgo/bridge/main.go`. Собирается в `bridge.exe`. Ничего на хосте не меняет —
слушает TCP-порт, держит один UDP-сокет на своём egress, пересылает датаграммы.

```
устройство  --TCP 15150-->  bridge  --UDP 443-->  162.159.198.2
   QUIC Initial           SOCKS5 UDP            QUIC Initial
```

```
BRIDGE_LISTEN     TCP, куда стучится устройство       0.0.0.0:15150
BRIDGE_ADVERTISE  адрес, который устройство считает нашим   10.0.2.2
BRIDGE_UPSTREAM   edge                                162.159.198.2:443
BRIDGE_BIND       egress, с которого уходит QUIC     192.168.0.4
```

## Почему один процесс, а не два

Связка «фронт + релей» держала один upstream-сокет на всех клиентов и запоминала адрес последнего,
кто заговорил. Ответ уходил в порт, который уже закрылся:

```
relay: first upstream datagram from 127.0.0.1:38110
relay: reply to 127.0.0.1:2181        <- мёртвый порт из давнего dial
front: relayed back 0 packets
```

101 датаграмма ушла, 38 ответов edge дал, до клиента дошёл ноль. У ответа не было пути домой,
потому что два процесса не видели состояние друг друга.

Здесь у сессии есть свой upstream-сокет и своя горутина чтения, а адрес назначения — поле самой
сессии. Устареть он не может: сессия не переживает соединение, которое её создало.

## Что стоило больше всего: отступ 3 вместо 4

SOCKS5-заголовок по RFC 1928 — четыре байта до адреса:

```
RSV(2) FRAG(1) ATYP(1) ADDR DST.PORT
```

```go
off := 3          // было
switch frame[off] {
case 1:
    off += 4
```

При `off := 3` верхний байт порта оставался в начале полезной нагрузки, и на edge улетал QUIC-пакет
с лишним байтом впереди. Edge такой пакет игнорирует без единого ответа. Симптом был идентичен
тупику: `up` растёт, `down` на нуле, ошибок нет.

```go
off := 4          // стало: RSV+FRAG+ATYP
switch frame[3] {
```

## Второй такой дефект: ответы читались не с того сокета

Ответ edge приходит на тот адрес и порт, с которого ушёл Initial. Первый вариант моста держал для
этого отдельный сокет — а отправлял из другого, поэтому в него никто ничего не слал:

```
up 60 pkts / 72060 bytes   down 0 pkts / 0 bytes
```

Читать надо с того же сокета, который шлёт.

## Что осталось за кадром

Мост — обход для измерения, а не фича приложения. Он нужен потому, что UDP гостя до edge
фильтруется: с устройства настоящий QUIC handshake не отвечает ни на одном порту edge, а TCP
соединяется сразу. Как только приложение сможет выбирать собственный исходящий сокет с тем же
egress, мост не нужен.
