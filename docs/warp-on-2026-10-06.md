## The fault

Read held the connection lock for its whole wait:

    c.mu.Lock()
    defer c.mu.Unlock()
    for len(c.inbuf) == 0 && !c.eof { ... poll ... }

and feed takes the same lock to append what arrived and to acknowledge it - and it acknowledges by writing
a capsule, which can block on the stream. So a reader holding the lock was waiting for a lock the writer
could not take because the reader had it. Go's TLS read blocked behind it, never saw the ServerHello that
was already in the buffer, and the handshake ended with a read timeout and a FIN:

    inbound 1280 bytes, 1228 payload, seq 3044710631   the whole flight arrives
    outbound 52 bytes                     ack 3044711859
    outbound 52 bytes  flags 0x011        FIN - Go gave up here with a read timeout

The lock is now taken and released around each poll. It reads the buffer, the end flag and the deadline, all
of which are under the lock on every pass, so a poll sees the same state - but it no longer holds the lock
while waiting, so feed can acknowledge what arrived while a reader is waiting for more.

## What it means

This was the last defect. Every layer below it is now measured correct by this same client on this carrier:

    UDP both ways      a DNS answer back through the tunnel
    TCP to port 80     HTTP/1.1 200 OK back through the tunnel
    TCP to port 443    a TLS 1.3 handshake, completed
    and then         the trace body, read through the tunnel, saying warp=on

Fourteen faults, each found by measuring rather than reasoning: a build that measured an older library, a
build script that reported failure as success, a discarded packet behind a capsule header, a frozen
acknowledgement, a pre-RFC varint, a bare header on the first acknowledgement, twenty option bytes where
twelve belong, a window in the wrong units on both the SYN and the segments after it, a fixed source port,
a fixed initial sequence, a carrier assumed not to relay TCP on a run that never asked it to, and this lock.
