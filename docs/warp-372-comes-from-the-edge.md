# 372 is the edge's own alert, sent after it stops talking

## The decisive source check

Every alert `aioquic` can raise, listed from `aioquic/tls.py`:

```
AlertCertificateExpired  AlertBadCertificate  AlertDecodeError  AlertIllegalParameter
AlertUnexpectedMessage   AlertDecryptError    AlertHandshakeFailure
```

`certificate_required` - number 116 - appears in the whole package exactly once, at the line that
defines it:

```
unknown_psk_identity = 115
certificate_required = 116      <- the only occurrence in aioquic
no_application_protocol = 120
```

It is never raised. Every raise site in the module was read, and none of them produces 116.

So `CRYPTO_ERROR + 116`, which is what the connection reports, cannot have been generated by this
client. It is the edge's alert, and it arrives inside a CRYPTO frame in a normal packet - which is why
the QUIC CONNECTION_CLOSE sniff found nothing and why `close()` was never called from Python.

## What this corrects

The previous reading was that the edge sends its last SETTINGS and then the client dies of loss
detection, reporting its own silence. The packet accounting was right and the interpretation was not:

```
from edge   : 0.094 Retry | 0.187 1200B | 0.187 943B | 0.296 59B H3 SETTINGS | (alert, no CONNECTION_CLOSE)
from client : Initial 1200B | 1200B | 1200B | 221B
```

The edge does send one more thing after the 59 bytes, and it is an encrypted TLS alert carrying
`certificate_required`. The connection then closes, loss detection never becomes the cause, and the
0x174 is the edge refusing in the one way TLS 1.3 allows once the handshake has completed -
post-handshake, on a flow that already looks healthy.

The same reading explains the certificate case. Presenting any certificate moves the alert to 49,
`access_denied`:

```
no certificate   alert 116  certificate_required
with a cert       alert  49  access_denied
```

and both end the flow within about a second, because both are refusals, not a timeout and not a
lost packet.

## What is settled, and what is not

Settled by measurement, each with the instrument that produced it:

- The edge is reachable from host and device, and speaks QUIC with ALPN h3.
- The handshake completes, the edge issues generous transport parameters (25000 bidi streams), and
  sends its H3 SETTINGS.
- The edge then sends a TLS alert: 116 without a certificate, 49 with one. Both are refusals and both
  end the connection in about a second.
- Requests sent at +50 ms do reach the wire, and changing their shape, target, timing, SNI or ALPN
  changes nothing, because the flow is already closed.
- The official client presents an identity that produces neither alert, and gets a tunnel.

Not settled: which certificate the edge accepts. Everything buildable from public inputs has been
tried - twelve subjects, Ed25519, CA:true, EKU variants, SAN, key usage, the registered key the
server had just stored - and every one returns 49. The schema recovered from the binary
(`RenewApiCertificateResponse { mtls: MtlsCertificate { certificate } }`) has a `certificate_id` that
Cloudflare issues, and the daemon builds the certificate from it using DPAPI- or TPM-held material.

**No `warp=on` measurement exists. The tunnel does not work.**

## The two alerts, and what they say in order

Both numbers are legitimate TLS alert descriptions in `aioquic`'s own enum, and neither is ever raised
by aioquic - so both arrive from the edge:

```
no certificate       -> alert 116 = certificate_required   at 1.219s
self-signed P-256    -> alert  49 = access_denied           at 1.093s
registered P-256     -> alert  49 = access_denied           at 1.109s
```

The edge is stating two things in sequence, and the second is the one that settles the shape of the
problem:

1. `certificate_required` - I need a client certificate.
2. `access_denied` - I received one and it is not acceptable.

If the second alert were a limitation of this client - an inability to answer a post-handshake
CertificateRequest, which aioquic 1.3 has no callback for - then presenting a certificate would change
nothing. It changes the alert from 116 to 49, which is only possible if the edge received the
certificate, parsed it, and applied a policy that rejected it.

That is also why every attempt produced 49 rather than something else, and why the registered-key
test proved nothing: the edge is not checking a key against a registration, it is applying a policy
to a certificate it has in hand. `InvalidPkixConfig` in the binary is the same word from the other
side.

## The wall, stated exactly

The edge on this network terminates a third-party QUIC client with a TLS refusal about its client
certificate, and refuses every certificate that can be built without Cloudflare-issued material. The
official client passes the same check on the same edge over the same path. The only known difference
between them is the certificate, and the certificate is built at registration by a daemon running as
LocalSystem, from secrets sealed by DPAPI under a SYSTEM-only ACL or by a TPM.

There is no network workaround for that, and none of the twenty-odd things measured in this project
changes it. The one thing that would is a minute with WARP enabled on this host, which is off limits.

**No `warp=on` measurement exists. The tunnel does not work.**
