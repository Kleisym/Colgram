# Every API call the client makes, and what each one returns here

## The complete list, from the service log

The service log names the API calls the official client makes, by count:

```
get_devices               122
get_registration_config    14
rotate_keys                 2
```

Plus the ones it calls at registration time. `get_registration_config` is the interesting one: it is
scoped to an existing registration rather than creating one, and it returned `Ok` at 13:02:24.906 - six
seconds after the tunnel came up - with an error history of four timeouts before it landed:

```
13:01:31.537  Spawning request  session_ctx=Consumer { reg_id: "254087e2-...", compliance: Normal }
13:01:31.539  Request failed, retrying in 2s     ReqwestError
13:01:43.543  Request failed, retrying in 3s     Timeout
13:01:56.544  Request failed, retrying in 4.5s   Timeout
13:02:06.804  Request failed, retrying in 6.75s  ReqwestError
13:02:13.577  Request failed, retrying in 10.125s ReqwestError
13:02:24.906  Request completed in 53368ms result=Ok
```

So the call exists, is reachable, and returns. What it returns is a `RegistrationConfig`, whose field
table is the one stored in `conf.json`:

```
own_public_key  registration_id  time_created  interface  endpoints  public_key  account
policy  valid_until  alternate_networks  dex_tests  install_root_ca  config_name
tunnel_key_data  device_identifiers  connector_config     (16 elements)
```

Notably it has no `mtls` field. The certificate is not in it either.

## Tried, and what came back

Six path shapes x two verbs, each with a fresh registration and the registration token in both
header spellings:

```
GET/POST  /v0a2158/accounts/{acct}/registration_config          404
GET/POST  /v0a2158/accounts/{acct}/reg/config                  404
GET/POST  /v0a2158/accounts/{acct}/config                      404
GET/POST  /v0a2158/accounts/{acct}/reg/{regid}/config          404
GET/POST  /v0a2158/accounts/{acct}                             404
GET/POST  /v0a2158/reg/{regid}                                 404
```

Every 404 is delayed 5 seconds by Cloudflare, which is anti-probing and makes sweeping pointless: a
wrong guess costs 5 s and returns exactly what a right guess with a wrong verb returns.

The same is true of the certificate paths, recovered from the binary as
`/v0/accounts/../reg/../client_certificates` and `/v1/accounts/../reg/../api-certificate/renew`,
and of the seven registration-field shapes. Nothing on the request side selects a different response.

## What the client does instead, and why 16 ms was never the mystery

The successful sequence, in the log:

```
13:02:07.078  TLS handshake completed   post_quantum_enabled: false, sni: None
13:02:07.091  Established QUIC connection with 192.168.0.4:61608 ---> 162.159.198.2:443
13:02:07.093  Starting MASQUE proxy task  idle_duration: 5s, keepalive_interval=1s
13:02:07.108  creating new flow for MASQUE request
13:02:08.334  Connected to 162.159.198.2:443 @ 696f29 : FRA
13:02:24.906  get_registration_config result=Ok
```

The tunnel was up at 13:02:08.334 and the API call only returned at 13:02:24.906. The tunnel did not
wait for it. Whatever satisfied the edge's 781 ms window was already in the daemon before the connect
started - produced at registration, stored under DPAPI or a TPM, and not fetched per connection.

That is why the 16 ms figure is not evidence of anything fast: it is the gap between a handshake and
a stream that was created from material already in hand, and the 1.24 s total is the sum of the
window plus the setup that follows.

## The audit, restated

| Where the material could be | Result |
|---|---|
| `C:\ProgramData\Cloudflare\` | 32 files, all logs, plus conf.json, settings.json, warp.db |
| `AppData\Local\Cloudflare` | two logs, ipc.log, the installer |
| Registry, both Cloudflare keys, all subkeys | 4 scalar values, no blobs |
| `warp.db` | 32768 bytes SQLite, no DPAPI signature, `tpm_keys` empty, unchanged since 27.08 |
| Public API, certificate paths | 404 on every shape, 5 s delay each |
| Public API, registration config paths | 404 on every shape |
| Public API, registration fields | seven shapes, identical response |
| Task dumps, snapshot logs | no public point, no key material |

The identity is generated by the daemon at registration, sealed by DPAPI under SYSTEM-only ACL, or
by a TPM, and is not derivable from anything the public API returns.

**No `warp=on` measurement exists. The tunnel does not work.**
