# Приложение само нашло рабочее реле — и оно не годится для WARP

Дата: 2026-10-01, 13:56. Это самая близкая к «своему обходу без внешнего релея» находка за
всю работу, и она же показывает, почему не годится.

## Что произошло

Приложение подняло локальный SOCKS5-фронт и подтвердило его нативной проверкой:

```
I ColgramProxyChain: SOCKS5 front 127.0.0.1:43397 -> socks5://144.24.111.128:1088
I ColgramProxyManager: Telegram DC route found through socks5://144.24.111.128:1088
I ColgramProxyManager: native check 127.0.0.1:43397 -> 464ms
```

`464ms` - это не локальная заглушка, а реальный ответ сети: фронт соединился с внешним SOCKS5-реле
и тот ответил. То есть **собственный обход внутри приложения работает** - для трафика Telegram.

## Почему WARP через него не идёт

Реле есть, и проверка это показала:

```
127.0.0.1:43397   socks5   associate refused: 7
```

Код 7 по RFC 1928 - «команда не поддерживается». UDP ASSOCIATE реле не даёт, а WARP-туннелю QUIC
нужен именно UDP до edge. Через CONNECT до edge:

```
127.0.0.1:43397   connect  no status: i/o timeout
HTTP_PROXY=127.0.0.1:43397 h3
  no proxy status: i/o timeout
```

Фронт занят: он обслуживает маршрут Telegram, и запрос извне к нему не обрабатывается.
Напрямую реле тоже не отвечает:

```
144.24.111.128:1088   socks5   associate refused: 7
144.24.111.128:1088   connect  i/o timeout
```

## Что из этого следует

Приложение умеет то, что нужно любому обходу: находить живое реле, поднимать локальный фронт и
проверять его нативно. Оно делает это для Telegram, где MTProto идёт через TCP.

WARP требует другого: UDP до edge, а этот класс рел - TCP-only. Проверено и кодом ответа (7), и
прямым запросом.

Так что зависимость от внешнего релея для WARP не устраняется на этом устройстве тем же приёмом,
которым приложение обходит блокировку для Telegram. Это разные требования к реле, а не разная
настройка одного и того же.

## Все семь локальных портов проверены

Приложение поднимает несколько фронтов. Каждый спрошен на UDP ASSOCIATE и CONNECT до edge:

```
127.0.0.1:34381   socks5   *** UDP ASSOCIATE GRANTED, relay port 1 ***
127.0.0.1:34381   connect  connection reset by peer
127.0.0.1:46617   socks5   associate refused: 7
127.0.0.1:46617   connect  i/o timeout
127.0.0.1:37999   socks5   no method reply
127.0.0.1:37999   connect  HTTP/1.1 502 Bad Gateway
```

И раньше:

```
127.0.0.1:43397   socks5   associate refused: 7
127.0.0.1:43961   socks5   no method reply
127.0.0.1:43517   socks5   no method reply
127.0.0.1:43511   socks5   *** UDP ASSOCIATE GRANTED, relay port 1 ***
127.0.0.1:38981   socks5   associate refused: 7
```

Три ответа на UDP ASSOCIATE - и все три с **портом 1**. Это фиктивное назначение: реле не
резервирует порт для передачи датаграмм, а отвечает формально. Реально UDP не переносит ни один из
семи.

## Про сами реле из пула

Они есть и работают - сети приложение собрало:

```
I ColgramProxyManager: socks source .../TheSpeedX/SOCKS-List/master/socks5.txt added 24
I ColgramProxyManager: socks source .../r00tee/Proxy-List/main/Socks5.txt added 23
I ColgramProxyManager: proxy harvest: 194 -> 241 Telegram candidates; reachable relays=16
I ColgramProxyManager: native check 127.0.0.1:43397 -> 464ms
```

Но напрямую с устройства они не отвечают:

```
47.251.127.154:1080    socks5   no method reply: i/o timeout
43.230.193.154:1080    socks5   no method reply: i/o timeout
```

Отвечает только локальный фронт приложения, и он для Telegram, а не для WARP.

Итог по всем источникам реле на этом устройстве: есть рабочие TCP-реле для Telegram, нет ни одного
рабочего UDP-реле, а собственный фронт приложения UDP не переносит.

## Почему «UDP ASSOCIATE GRANTED, port 1» - не реле с UDP

Ответ на сырой UDP ASSOCIATE разобран побайтно:

```
printf '\x05\x03\x00\x01\x00\x00\x00\x01\x00\x01' | nc 127.0.0.1 34381 | xxd
  00000000: 0500 0501 0001 0000 0000 0000
```

`05 00` - SOCKS5 success, а дальше `01 0001` - **порт 1**. То есть фронт ответил на UDP ASSOCIATE
формально и вернул несуществующий порт. Никакой ретрансляции датаграмм за этим нет.

И это видно в его коде:

```java
ColgramProxyChain.java:412   final int port = ...;
   upstream = connectThrough(uplink, host, port, CONNECT_TIMEOUT_MS);
```

Одна ветка, одна команда - CONNECT. Ветки для UDP ASSOCIATE в файле нет, поэтому запрос с командой
`0x03` обрабатывается как CONNECT с портом 1 и заканчивается успешным ответом с бессмысленным
адресом.

Раньше это выглядело как «реле дало UDP». Теперь видно, что это отказ, оформленный как согласие.

## Реле доступно напрямую, но по-прежнему TCP-only

Последний непроверенный вариант - реле без локального фронта:

```
toybox timeout 6 nc 184.178.172.5 15303   RC=0        <- TCP до реле есть

184.178.172.5:15303   socks5   associate refused: 7
184.178.172.5:15303   connect  no status: i/o timeout
```

TCP до реле от устройства открыт, и это важно: значит, ограничение не в доступе к реле, а именно в
том, что реле не переносит датаграммы.

Через локальный фронт - то же самое, плюс он занят:

```
127.0.0.1:41865   socks5   associate refused: 7
127.0.0.1:41865   connect  i/o timeout
HTTP_PROXY=127.0.0.1:41865 h3
  no proxy status: i/o timeout
```

## Полный список проверенных egress

| Источник | TCP до реле | UDP через него | Доходит до edge | Годится для WARP |
|---|---|---|---|---|
| `184.178.172.5:15303` напрямую | да | отказ 7 | не проверялось | нет |
| локальный фронт приложения | только своему клиенту | отказ 7 | нет | нет |
| VPN-прокси хоста `10808` | да | порт 1 | нет | нет |
| `144.24.111.128:1088` | через фронт | отказ 7 | нет | нет |
| **мост на хосте, `192.168.0.4`** | да | **да** | **да** | **да** |

Единственная строка, где UDP есть и edge отвечает, - мост на хосте. Он не обход блокировки: у
устройства за NAT один адрес, и выбрать egress, с которого Cloudflare отвечает, нечем.
