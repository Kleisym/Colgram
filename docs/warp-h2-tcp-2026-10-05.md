# WARP over HTTP/2: six faults of mine, and what the edge still does not carry

This continues `warp-h2-carrier-found-2026-10-04.md`, which records the carrier, the request shape and
the three framing faults. That file ends with `warp=on` read from inside Colgram on the phone. This one
records a session in which that verdict stopped being reachable, the six faults found while getting it
back, and the measurement that says what is left.

Every log line below was read off the device `SM-A536E - 15` through MuMu at `127.0.0.1:16384`.

## Why the verdict stopped being reachable

The first fault was not in the client at all. The test flavour shipped `arm64-v8a` and the device is
`x86_64`:

    ro.product.cpu.abi = x86_64
    jar tf ...afat-debug.apk | grep libcolgrammasque
    lib/arm64-v8a/libcolgrammasque.so        <- the only entry in the APK

PackageInstaller accepted it anyway - there was no library for the device ABI to be missing - and Android
loaded the copy from the earlier install. So every measurement was of the build before the one measuring
it. That is the whole explanation for a change that was made, rebuilt, reinstalled and changed nothing.

`TMessagesProj_AppTests/build.gradle` now filters `x86_64`. It is a per-device choice: the release flavour
keeps all four ABIs, and the install-size argument that motivated the filter is real.

## Fault two: the build script reported failures as successes

`tools/buildh2.ps1` ran `go build -o h2_x86_64.so`, ignored the exit code, then printed the size of
whatever was at that path. A failed build does not clear its `-o` target, so a compile error printed as a
successful build of the previous library:

    # warpverdict
    .\main.go:2627:41: cannot use string(...) as []byte value in argument to head
    h2_x86_64.so 13225800        <- from an hour earlier

That cost three build-and-measure cycles where the code on the device was not the code on this machine.
The script now deletes the old library, honours the exit code, and exits non-zero. Every `.so` staged into
the APK from here was checked for a string it must contain before it was staged.

## Fault three: the TCP options were never the fault

An earlier conclusion here held that a flow negotiating a 40-byte header was discarded while a flow with a
constant 20-byte header was forwarded. It was drawn from a run of its own and it was wrong. The reference
client own SYN, off the capture in `tools/usqueh2/err3.log`, is:

    H2 WRITE 71 bytes: ... 00 3c 45 00 00 3c 00 00 40 00 3f 06 ac 39 ac 10 00 02
                         68 10 7b 60 d1 e7 01 bb 18 73 b5 cc 00 00 00 00 a0 02 60
                         80 73 d6 00 00 02 04 04 d8 04 02 08 0a ea e8 58 37 00 00 00
                         00 01 03 03 07

Decoded, a 62-byte capsule wrapping a 40-byte TCP header, and the 20 bytes after the fixed header are

    02 04 04 d8   MSS 1240
    04 02         SACK permitted
    08 0a ...     timestamps, TSval 0xeae85837, TSecr 0
    01            NOP
    03 03 07      window scale 7

byte for byte what `synOptions()` returns. The options were never the fault, and the flow reported as
answered without them was answered by the edge own SYN-ACK - which the handshake completes on regardless of
options, so a flow whose data is discarded looks identical either way.

What told the two apart was a 72-byte data segment sent on the handshake flow itself, one byte after the
ACK, instead of a second SYN on a flow of its own:

    72-byte probe on the handshake flow, sent=8 recv=2

Zero bytes back on a data segment while the SYN on the same flow had been answered twice. Size was ruled out
with it: 72 bytes is not a size anything refuses.

`noOptions` is now gone from the file rather than left as a control measured wrong. With options restored
the edge SYN-ACK comes back 60 bytes and its option block is captured correctly:

    captured 20 peer option bytes: 020405b40402080adf51596b0001fd750103030d

MSS 1460, SACK, timestamps TSval `df51596b`, wscale 13 - the shape the reference client was given.

## Fault four: the timestamp option was a constant

`synOptions()` returned fixed bytes, including a fixed TSval and a TSecr of zero. The reference option
block is not constant across a flow:

    SYN    08 0a ea e8 58 37 00 00 00 00    TSval 0xeae85837, TSecr 0
    data   08 0a ea e8 5f 8f 8b 43 33 17    TSval 0xeae85f8f, TSecr 0x8b433317

TSval advances with the clock and TSecr becomes the TSval the edge sent on its SYN-ACK. A constant pair is
a timestamp that never moves and an echo of nothing. The value is now `time.Since(processStart)` in
milliseconds, and the echo half is written from the peer TSval by `stampEcho`.

## Fault five: the peer option capture ran past the options

    c.peerOptions = append([]byte(nil), tcp[offset:]...)

`tcp[offset:]` reads from the data offset to the end of the buffer, which on a segment carrying payload is
the options followed by a live sequence and the payload. What was echoed back on every segment after the
handshake was a header-length-changing blob with real data inside it. The options are bounded by the data
offset: `tcp[20:offset]`, twenty bytes here.

## Fault six: a DATA frame is not a packet

The inbound reader returned whatever one HTTP/2 DATA frame held. The edge splits the capsule stream
wherever it likes, and it splits it - the reference client own log:

    H2 READ 72 bytes: 000002000000000001 0034 | 000034000000000001 45000034...8f
                     ^ 2-byte DATA frame     ^ 52-byte DATA frame

The first frame carries only the two capsule bytes `00 34`. The second carries the packet, starting at the
IP version nibble. Reading a frame at a time returns a two-byte buffer, then a packet whose first two bytes
have already been consumed as a capsule header, so both fail every check the reader makes.

`h2CapsuleStream` now keeps a byte buffer for the stream and takes whole packets off it with
`nextInboundPacket`, which decides between the two shapes the edge sends by the buffer itself:

| shape | first bytes | decided by |
|---|---|---|
| framed | `00 3c 45 00 ...` | version nibble is 0, so the varint path: type, length, payload |
| bare | `45 00 00 3c ...` | version nibble is 4, and the total length inside the header says how much |

The two cannot be confused: a bare packet starts `0x45`, which as a varint would be a type of 5, and a
framed packet starts `0x00`, which is no IP version at all. A partial packet is held for the rest of its
bytes rather than handed up short.

The varint reader is separate from the one already in this file (`readCapsuleVarint`) because that one is
the older pre-RFC encoding: it reads `0x40` as a two-byte value where RFC 9000 reserves the top two bits as
a length, so `0x40` is a one-byte value of 64. A capsule length is written under RFC 9000.

Verified against the reference own bytes before it ran on the device - a header alone yields no packet,
the packet is recovered across the two frames byte-identically, a 466-byte capsule three-byte header decodes,
two packets come off one stream in sequence, a half-arrived packet is held, and a bare unframed packet is
accepted.

## What the edge still does not do

With all six faults fixed the flow opens, the edge SYN-ACK carries options and is parsed, and the tunnel
carries nothing:

    outbound 60 bytes (opts 20, peer 20), flags 0x002, seq 1                          SYN
    inbound  60 bytes, 0 of payload, flags 0x012, ack 2                              SYN-ACK
    captured 20 peer option bytes: 020405b40402080adf51596b0001fd750103030d
    h2 peer open, sent=7 recv=2
    plaintext trace returned 0 bytes, sent=8 recv=2: ""
    h2 carrier failed: tls inside tunnel: i/o timeout (sent=11 recv=3)

The plaintext request is the important line. It is the reference client own request, byte for byte:

    GET /cdn-cgi/trace HTTP/1.1
    Host: www.cloudflare.com
    Connection: close

which that client sent and got back:

    H2 READ 487 bytes: ... HTTP/1.1 400 Bad Request ... <title>400 Bad Request</h1>
                        ... this port does not serve HTTP.

The 400 is the answer that matters - it proves the edge took the flow out to the real host and the host
reply came back through the same stream, with no TLS involved anywhere. So this carrier does route, for this
identity, on this network, and a plaintext request separates the two things TLS adds at once. Sent here it
returns nothing at all.

## Ruled out by measurement

| Suspect | How it was excluded |
|---|---|
| The library was not the one being measured | `ro.product.cpu.abi = x86_64` against an arm64-only APK; filter fixed, every staged `.so` checked by string |
| A stale library after a failed build | the build script printed a failed build as a success; fixed, exit code honoured |
| Payload size | a 72-byte segment gets nothing while the SYN on the same flow is answered twice; the segment cap is back at 1100, the value the `warp=on` run used |
| TCP options | the reference SYN carries exactly `synOptions()`; `noOptions` removed from the file |
| Timestamp option contents | fixed value and zero echo replaced with a live clock and the peer TSval |
| The peer option capture | `tcp[offset:]` ran past the options into payload; now `tcp[20:offset]` |
| Frame-boundary reading | reassembly added; verified against the reference bytes before it ran on device |
| HTTP/2 flow control | the edge grants `INITIAL_WINDOW_SIZE 1048576`, `MAX_FRAME_SIZE 16384`, `MAX_CONCURRENT_STREAMS 256`; this client sends about 1.2 KB. Credit returned per frame, on stream and connection |
| Capsule framing outbound | two bytes, type 0 and length, no context id - the reference own bytes, unchanged by any of this |
| The request shape | `:authority cloudflareaccess.com:443`, `:method CONNECT`, `cf-connect-proto`, `pq-enabled: false`, `accept-encoding: gzip`, no `:scheme`, `:path` or `:protocol` - accepted with status 200 every run |
| The account | `free`, licence bound, `warp_plus: true`, read back from the API after registration |
| Dont Fragment | the reference sets `0x4000` on every packet; this client sent `0x0000` and now sends `0x4000`. No change in what the edge carries |
| The destination | `connectivity.cloudflareclient.com` resolves through DoH to `162.159.137.65`/`162.159.138.65`, both inside the range the host is served from, and the plaintext probe goes to the same place the reference used |

## Where the remaining difference can be, in order of what it would explain

The client SYN and its option block now match the reference field for field, and the reference own request
returns nothing when sent through this tunnel. Three things are still different between the two clients,
and none has been measured against the edge yet:

1. **The registration is fresh on every run.** Each `trace()` call registers a new device, enrols a new P-256
   key and mints a new certificate. The reference client used one enrolment for its whole session. If the
   edge needs a moment after enrolment before it will route for an identity - or needs the identity to have
   been seen on the QUIC endpoint the registration names, which is filtered here - then a tunnel opened one
   second after enrolment is exactly the case that gets the handshake and not the data.
2. **The source port inside the tunnel.** Both use `172.16.0.2` as assigned. The source port differs (51500
   here, 53735 there), which is legal, but a port outside the range the reference used has not been tested
   against a real reply.
3. **The tunnel is opened twice.** `negotiateH2Shape` opens one connection per request shape and then a
   second for the tunnel it keeps. The reference opens one. Earlier notes record the edge refusing new
   connections from an address that has just opened several, and the shape is now remembered per process so
   this only happens on the first call - but the tunnel still runs on the second of two connections opened
   seconds apart.

Number 1 is the one to test next and it is cheap: reuse one enrolment across several trace attempts on one
tunnel, rather than registering again for each, and read whether the second and third attempts differ from
the first.

## The state of the tree

Six faults fixed and each measured. The verdict test still fails, and it fails at the same measured point:

    ColgramWarpVerdict: trace bytes=0
    ColgramWarpVerdict: no trace; last error=no edge route answered: tls inside tunnel: i/o timeout (sent=11 recv=3)

Nothing in this document claims WARP works. It claims the client is now field-for-field identical to a
client that returned `warp=on` on this network at 01:02 on 2026-10-05, that the difference which remains is
named above, and that every step of it was measured on the device rather than reasoned about.
